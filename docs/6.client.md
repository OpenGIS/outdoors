# Client-side rendering

> `style.json` is validated against the [MapLibre Style Specification](https://maplibre.org/maplibre-style-spec/) at build.

> [!NOTE]
> Currently the style has only been tested with MapLibre GL JS!

> [!WARNING]
> **Known Issues**
>
> - **Metric-only.** The style is metric-only.

## Usage

Loading the style in MapLibre GL JS is a matter of pointing a `Map` at it:

```js
import maplibregl from "maplibre-gl";

const map = new maplibregl.Map({
  container: "map", // a named <div> in your page
  style: "style.json",
});
```

## Metric vs Imperial

The style ships **metric-only**: elevation labels use metres (`m`) — contour labels and the basemap's peak labels. There is no feet variant in the style.

### Contours

Unit switching can be achieved at runtime, before the map parses the style. The compare app does this in [`applyImperialContours()`](../dev/src/App.vue): a recursive expression walker ([`toImperial()`](../dev/src/App.vue)) that converts the `contour-labels` `text-field` from metres to feet — wrapping the `round` argument in `["*", ["get", "ele"], 3.28084]`, swapping the `"m"` suffix for `"ft"`, and leaving the index-contours-only `case` expression intact so only index contours get labelled. The conversion is gated by the `CONTOURS_TO_IMPERIAL` constant in [`dev/src/App.vue`](../dev/src/App.vue).

### Peak Heights

Peak labels are native to the basemap (`Mountain peak labels` / `Volcano peak labels`) and are not patched by the compare app — only the `contour-labels` layer is converted.

## The Compare App

The dev app (`dev/`) renders the outdoor style against external providers. The default comparison provider is the **OpenGIS Basemap** itself — `opengis-basemap` in [`dev/src/providers.json`](../dev/src/providers.json) (label "OpenGIS Basemap", style URL `https://www.ogis.org/basemap/style.json`), selected by `DEFAULT_PROVIDER_KEY` in [`dev/src/composables/useProviderSelection.js`](../dev/src/composables/useProviderSelection.js). The selection is persisted in `localStorage`; providers that require an API key prompt for one, stored locally in the browser only.

### View modes

A view-mode control sits beside the provider dropdown, choosing how the outdoor style is compared against the provider:

- **Overlay** — a swipe comparison via `@maplibre/maplibre-gl-compare`, with a draggable divider revealing one map over the other.
- **Side by side** — two maps in equal halves, synchronised on pan, zoom, bearing and pitch.

The choice is persisted in `localStorage` under `outdoors_dev_viewMode` and applied by [`applyViewMode()`](../dev/src/App.vue); side-by-side sync is handled by [`createMoveSync()`](../dev/src/App.vue).

### Initial camera

The left map is created with `hash: true`, so it reads its camera from the URL fragment (`#zoom/lat/lng[/bearing[/pitch]]`). The right map has no hash of its own, so [`parseHashCamera()`](../dev/src/hashCamera.js) parses the same fragment and seeds the right map's centre, zoom, bearing and pitch — both panes paint the hash view from the first frame instead of the right pane briefly starting at the default z3 world view. A missing or malformed hash returns `null`, leaving the app's default centre and zoom in place; absent bearing and pitch default to 0.

### Attribution

Both maps set `attributionControl: { compact: true, customAttribution: … }`. The right map — the pane rendering the outdoors style — passes the style's build-owned `metadata.attributionLine` ([`ATTRIBUTION.LINE`](1.build.md#attribution)), falling back to the bare heart MapLibre link `MAPLIBRE_ATTRIBUTION` in [`dev/src/App.vue`](../dev/src/App.vue) when the metadata is absent; the left provider-comparison map always keeps `MAPLIBRE_ATTRIBUTION`, which also replaces the control's stock MapLibre link. The screenshot harness preloads `/style.json`, passes the parsed style object to the map and reads the same `metadata.attributionLine` as `customAttribution` — same fallback — in [`scripts/screenshots/harness.html`](../scripts/screenshots/harness.html). The line carries every credit verbatim, so maplibre-gl's substring dedupe collapses the per-source attributions into it and each control renders one seamless line with no `|` separators. See [Build Script](1.build.md).

### Tooling hook

Once both maps exist, the app exposes them as `window.__outdoorsMaps = { leftMap, rightMap }`. External tooling — notably the [benchmark harness](9.performance.md) — uses the hook to reach the maps in any build, including the production `demo/` bundle where Vue strips the dev-only `__vueParentComponent` back-reference. The hook is behaviour-neutral.

### DEM overlays

Two checkboxes sit beside the provider and view-mode controls, toggling DEM relief on the **left (provider) map** so a provider can be compared against the outdoor style like-for-like in 3D:

- **Hillshading** — a `compare-hillshade` hillshade layer, using the same zoom-ramped exaggeration as the style's own hillshade.
- **3D terrain** — enables the map's `terrain` property at a fixed **1.2×** exaggeration, matching the right pane.

Both are backed by a dedicated `raster-dem` source (`compare-dem`) pointed straight at the Mapterhorn tiles (`tiles.mapterhorn.com`, Terrarium encoding, 512 px, maxzoom 15, `© Mapterhorn` attribution) and default to **on**; each persists independently in `localStorage` (`outdoors_dev_demHillshade`, `outdoors_dev_demTerrain`). [`useDemOverlay()`](../dev/src/composables/useDemOverlay.js) owns the state, and its `attach()` re-applies the overlays after every `style.load` so they survive provider switches; the source is removed only once both toggles are off. The declared maxzoom matches the style's `demSource` — the tile size does not: the left pane keeps Mapterhorn's served 512 px, while the style declares 256 px to cut terrain work. Both panes overzoom the same complete z15 tiles rather than requesting Mapterhorn's gap-ridden z16.

Both maps' DEM sources also take the shared terrain LOD from [`dev/src/terrainLod.js`](../dev/src/terrainLod.js): the left map applies it to `compare-dem` after each source add, and the right map applies it to every `raster-dem` source derived from the parsed style on `style.load`. The LOD is a map-level option, so consumers of `style.json` must apply it themselves — see [Performance](9.performance.md). The right map's DEM remains style-driven from `style.json`.
