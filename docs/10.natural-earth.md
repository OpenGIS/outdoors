# Natural Earth & the Ground Raster

> The calibrated vector ground band and how the Esri World Imagery raster is blended over it.

## What "natural earth" means here

In this project **natural earth** is the calibrated landcover/landuse **vector** ground — the fills the OpenMapTiles schema draws for grass, wood, rock, sand, farmland, heath, built-up landuse and the like. It is the ground truth that sits beneath the ground raster: the raster composites over it rather than replacing it, so where the imagery is absent, stale or simply too coarse, the vector ground still carries the map.

> [!NOTE]
> Natural earth here is **not** the Natural Earth dataset and **not** a shaded-relief raster. The basemap's former `ne2_shaded` relief raster is no longer inherited by the style; relief now comes from the Mapterhorn DEM hillshade (see [Elevation & Terrain](5.dem.md)).

The band is recoloured by [`applyNaturalEarthPalette()`](../scripts/build.mjs) — the landcover/landuse half of the `TERRAIN_PALETTE` toggle — while the earthy canvas floor beneath it is recoloured by [`applyCorePalette()`](../scripts/build.mjs) from `COLOURS.TERRAIN.BACKGROUND`. Both read their values from the central `COLOURS` object (`COLOURS.TERRAIN`, `COLOURS.LANDCOVER`, `COLOURS.LANDUSE`).

### The natural-earth palette

[`applyNaturalEarthPalette()`](../scripts/build.mjs) maps each basemap landcover/landuse layer family to one `COLOURS` key:

| Basemap layer family                                                                          | `COLOURS` key                   |
| --------------------------------------------------------------------------------------------- | ------------------------------- |
| Grass, meadow, garden, recreation ground, cemetery, wetland/swamp, marsh, allotments, stadium | `COLOURS.TERRAIN.GRASS`         |
| Wood, forest, mangrove                                                                        | `COLOURS.TERRAIN.WOOD`          |
| Rock, scree, bare rock                                                                        | `COLOURS.LANDCOVER.ROCK`        |
| Sand, dune, beach                                                                             | `COLOURS.TERRAIN.SAND`          |
| Farmland, farm, orchard and vineyard                                                          | `COLOURS.LANDCOVER.FARMLAND`    |
| Heath, scrub                                                                                  | `COLOURS.LANDCOVER.HEATH`       |
| Residential                                                                                   | `COLOURS.TERRAIN.RESIDENTIAL`   |
| Military                                                                                      | `COLOURS.LANDUSE.MILITARY`      |
| Quarry                                                                                        | `COLOURS.LANDUSE.QUARRY`        |
| Glacier                                                                                       | `COLOURS.TERRAIN.ICE`           |
| Glacier outline (the outline **line**)                                                        | `COLOURS.WATER.GLACIER_OUTLINE` |

The glacier outline is the non-obvious reuse: its line colour lives in the **water** palette even though the fill it edges is terrain. The `Background` canvas floor is the one ground fill outside this function — recoloured by `applyCorePalette()` from `COLOURS.TERRAIN.BACKGROUND`.

**Calibrated** here means these fills, and the canvas floor beneath them, are matched to the reference imagery so the vector ground and the raster read as a single surface; see [Re-tuning the ground](#re-tuning-the-ground) for the stops and levers.

## The render stack

The build orders its work through a single [`RENDER_STACK`](../scripts/build.mjs) array. Each entry is a **group** — a band of the rendered map — and groups are listed bottom-to-top: the `Background` canvas first, the POI labels last. [`applyModifications()`](../scripts/build.mjs) walks the groups in order and runs each group's steps whose predicate is true, then runs the cross-group [`FINISHING_PASSES`](../scripts/build.mjs).

| id              | Title                 | What it owns                                                                                                | Behaviour under the ground raster                                                                  |
| --------------- | --------------------- | ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `core`          | Core canvas           | The `Background` floor — the earthy reddish-grey canvas tone.                                               | Unchanged: the raster sits above the floor, which only shows where the imagery does not.           |
| `natural-earth` | Natural-earth vectors | The calibrated landcover/landuse fills plus park differentiation (fill, national-park boundary and labels). | Retained beneath the raster; the imagery composites over them at `GROUND_RASTER_OPACITY`.          |
| `ground-raster` | Ground raster         | The `satellite` layer over the `esri-satellite` raster source.                                              | This is the blended ground itself; it sits beneath the water and every later vector layer.         |
| `water`         | Water                 | Water fill and waterway line recolouring.                                                                   | Water stays above the raster; the fills are made translucent so they read as a palette tint.       |
| `terrain`       | Terrain & contours    | The Mapterhorn DEM source, hillshade, 3D terrain, hosted contours and contour labels.                       | The hillshade composites relief over the raster; the finishing pass recedes the contour opacities. |
| `roads-paths`   | Roads & paths         | Surface-aware roads, the low-zoom path overlay and the native path family.                                  | Mostly unaffected; the finishing pass tones the man-made surfaces, path casings and road labels.   |
| `buildings`     | Buildings             | The upstream `Building` fill (below the roads).                                                             | The finishing pass swaps it for `building-outline` and `building-3d` only while the raster is on.  |
| `borders`       | Borders               | The upstream administrative boundaries.                                                                     | Unaffected by the ground raster.                                                                   |
| `labels-poi`    | Labels & POI          | The basemap POI icon rewrite plus the `outdoor-amenities` and `outdoor-poi` overlays.                       | Unaffected, except the finishing pass widens the halos on the small road and street labels.        |

Groups whose `steps` array is empty document a band owned entirely by the upstream basemap; their metadata still describes the band. The metadata on every group (`title`, `summary`, `palette`, `satellite`, `layers`) is documentation only and never affects the build.

### How the stack is defined and consumed

Each `RENDER_STACK` group is an object with:

- `id` and `title` — the band's stable name and human label.
- `summary` / `satellite` — prose describing what the band owns and how it behaves under the raster.
- `palette` — the `COLOURS` sub-objects (or keys) the band reads.
- `layers` — the base-style layer ids the band is responsible for.
- `steps` — an array of `{ when, run }` pairs: `when()` gates the step on a `FEATURES` toggle (or is always true), and `run(style, ctx)` applies it.

[`applyModifications(style, spriteKeys)`](../scripts/build.mjs) builds a shared `ctx` (the basemap sprite keys, passed to the steps that need them), then:

1. walks `RENDER_STACK` bottom-to-top, running every step whose `when()` returns true; then
2. walks `FINISHING_PASSES`, running every pass whose predicate is true.

`FINISHING_PASSES` is deliberately a separate list because its overrides must beat every group above — the imagery legibility pass is the last thing that runs, so its `setPaint` overrides win over the contours, roads and paths. The stack is the single source of truth for render order; mutating a group's metadata cannot change the output.

## The blend

The `SATELLITE_GROUND` toggle places the **Esri World Imagery** raster _above_ the natural-earth vectors rather than beneath every vector layer. [`applySatelliteGround()`](../scripts/build.mjs) adds the `esri-satellite` `raster` source and the `satellite` layer at the **first water layer** ([`waterStackIndex()`](../scripts/build.mjs)), falling back to directly above the `Background` floor if no water anchor exists. The raster therefore sits above the calibrated landcover/landuse fills but beneath the water, hillshade and every later vector layer.

Because the vectors are retained underneath, the imagery is composited, not substituted: the vector ground reads through wherever the raster is translucent or has no data. The raster's `raster-opacity` is a linear zoom interpolation — from `GROUND_RASTER_OPACITY_LOW_ZOOM` at z8 easing down to `GROUND_RASTER_OPACITY` by z14. The higher low-zoom value lets more of the coarser low-zoom imagery show; by z14 the raster settles at its base opacity over the fully detailed vectors.

At its base opacity the raster supplies the bulk of the visible ground, so the canvas and the natural-earth vectors intentionally contribute a minority and surface only where the imagery is absent or translucent. Pushing either opacity toward full opacity flattens the calibrated vectors toward invisible, so tune `GROUND_RASTER_OPACITY` and `GROUND_RASTER_OPACITY_LOW_ZOOM` together against the reference stops (see [Re-tuning the ground](#re-tuning-the-ground)).

The water fills stay above the raster and are made translucent by [`applyWaterTint()`](../scripts/build.mjs), which sets the `fill-opacity` of `Water` and `Water intermittent` to `WATER_TINT_OPACITY`. The waterway lines keep their palette colour; only the fills become a tint.

### Why the water tint — the flagship data fusion

The water tint is the project's clearest example of **data fusion** rather than layering. The vector ocean polygon encodes a mean sea level; the satellite imagery is a snapshot of the actual water surface at capture time (tide, season, recent weather). Drawn translucent over the imagery, the mean vector water and the instantaneous raster water combine: the vector fill carries a consistent colour and shoreline across every zoom, while the imagery supplies the real water detail underneath. Coasts read more realistically than either layer alone, and the vector ocean no longer punches an opaque hole through the imagery.

## Re-tuning the ground

The blend is calibrated against real imagery, not against the vector palette alone. To re-tune it:

1. Run the compare app in development (`npm run dev`).
2. Switch the view mode to **Side by side**.
3. Set the provider to **Esri World Imagery**.
4. Turn on the left map's **Hillshading** and **3D terrain** so both panes share the same relief reading.
5. Sweep the **reference stops** below — each exercises a different landcover mix.
6. Capture before/after stills of a stop before changing a lever, so each change is judged against the same view.
7. Change one lever at a time: the `COLOURS` palette sub-objects, `GROUND_RASTER_OPACITY` / `GROUND_RASTER_OPACITY_LOW_ZOOM` and the `GROUND_RASTER_RAMP_ZOOM_LOW` / `GROUND_RASTER_RAMP_ZOOM_HIGH` ramp zooms, `WATER_TINT_OPACITY`, and the `IMAGERY_*` / `BUILDING_*` config (including `IMAGERY_PARK_BOUNDARY_OPACITY`).

## The strip carry-over

Earlier versions of the build removed the base style's large opaque fills outright when the raster was enabled, through the `SAT_STRIP_*` arrays (`SAT_STRIP_LANDUSE_FILLS`, `SAT_STRIP_LANDCOVER_FILLS`, `SAT_STRIP_OUTLINE_STROKES`, `SAT_STRIP_OTHER`). Those arrays have retired: with the raster now blended over the calibrated vectors, the vectors are retained instead.

What remains is [`SAT_STRIP_LAYERS`](../scripts/build.mjs), a single carry-over list consumed by [`applyGroundRetention()`](../scripts/build.mjs). The function calls [`removeLayers()`](../scripts/build.mjs) over that list, so any layer that must still be stripped when the ground raster is enabled can be added there and removed by exact id — missing ids are skipped silently, keeping the build robust against upstream renames. The `removeLayers()` loop is retained precisely so that escape hatch stays available.

> [!NOTE]
> `applyGroundRetention()` is gated by `SATELLITE_GROUND`; when the toggle is off it is a no-op.

The same legibility pass that runs last over the imagery also fades the park boundary lines (`National parks`, `National park outline`) so they read as ground detail rather than a bright overlay.

## Data-fusion opportunities

The blend opens a family of data-fusion wins where a stable vector layer and a dynamic or detail-rich raster each supply what the other lacks. Candidates, in rough order of confidence:

- **Water vs mean sea level** _(flagship)_ — the translucent vector ocean over the imagery reconciles a consistent mean-sea-level shoreline with the captured water surface, so tidal and seasonal coastlines read more naturally.
- **Stable landcover over seasonal imagery** — the calibrated landcover/landuse vectors are season-stable, while imagery behind them carries seasonal change and mosaic stitching between captures; the vector ground averages out those seams without discarding the imagery detail.
- **DEM hillshade relief** — the hillshade composites over the raster (it sits above it in the stack), giving flat or low-contrast imagery the same relief reading the vector-only style has.
- **Shoreline stability** — the vector shoreline is constant across zooms, so it can anchor a coastline that imagery mosaics would otherwise render inconsistently between captures and zoom levels.

Each is a rationale for the blend, not a claim that the current style has been tuned for it.
