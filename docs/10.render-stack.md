# Render Stack

> The ordered bands of the generated style and the passes that override them.

Render order is the spine of the build: every modification lands at a defined point in one bottom-to-top band list, and the finishing passes run after the walk so their overrides win. That order — not the order the functions happen to appear in — decides what draws over what.

## The render stack

The build orders its work through a single [`RENDER_STACK`](../scripts/build.mjs) array. Each entry is a **group** — a band of the rendered map — and groups are listed bottom-to-top: the `Background` canvas first, the POI labels last. [`applyModifications()`](../scripts/build.mjs) walks the groups in order and runs each group's steps whose predicate is true, then runs the cross-group [`FINISHING_PASSES`](../scripts/build.mjs).

| id              | Title                 | What it owns                                                                                                                                                                                     | Behaviour under the ground raster                                                                                                                                  |
| --------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `core`          | Core canvas           | The `Background` floor — the earthy reddish-grey canvas tone.                                                                                                                                    | Unchanged: the raster sits above the floor at 0.8 base / 0.9 low-zoom opacity, so the floor composites through everywhere at 10–20%.                               |
| `natural-earth` | Natural-earth vectors | The calibrated landcover/landuse fills plus park differentiation (fill, national-park boundary and labels).                                                                                      | The landcover/landuse fills are retained beneath the raster; the imagery composites over them at `GROUND_RASTER_OPACITY`. Park boundaries and labels sit above it. |
| `ground-raster` | Ground raster         | The `satellite` layer over the `esri-satellite` raster source.                                                                                                                                   | This is the blended ground itself; it sits beneath the water and every later vector layer.                                                                         |
| `water`         | Water                 | Water fill and waterway line recolouring.                                                                                                                                                        | Water stays above the raster; the fills are made translucent so they read as a palette tint.                                                                       |
| `terrain`       | Terrain & contours    | The Mapterhorn DEM source, hillshade, 3D terrain, contours and contour labels.                                                                                                                   | The hillshade composites relief over the raster; the finishing pass recedes the contour opacities.                                                                 |
| `roads-paths`   | Roads & paths         | Surface-aware roads, the low-zoom path overlay and the native path family.                                                                                                                       | Mostly unaffected; the finishing pass tones the man-made surfaces, path casings and road labels.                                                                   |
| `buildings`     | Buildings             | The upstream `Building` fill (below the roads).                                                                                                                                                  | The finishing pass swaps it for `building-outline` and `building-3d` only while the raster is on.                                                                  |
| `borders`       | Borders               | The upstream administrative boundaries.                                                                                                                                                          | Unaffected by the ground raster.                                                                                                                                   |
| `routes`        | Waymarked routes      | The `outdoor-routes` overlay for hiking and cycling: cycling beneath hiking, each with its own marked tiers and neutral unmarked tier; ways shared by both enabled activities paint mixed green. | Unaffected by the ground raster; routes sit above the boundaries and below every label.                                                                            |
| `labels-poi`    | Labels & POI          | The basemap POI icon rewrite plus the `outdoor-amenities` and `outdoor-poi` overlays.                                                                                                            | Unaffected, except the finishing pass widens the halos on `Road labels` and the five road shield layers.                                                           |

An empty `steps` array means the band has no band-level steps, not that it is untouched: `buildings` has none, yet `FINISHING_PASSES` removes the `Building` fill and adds `building-outline`/`building-3d` when the satellite ground is enabled, while `borders` is left entirely to the upstream basemap. Group metadata still describes the band. The metadata on every group (`title`, `summary`, `palette`, `satellite`, `layers`) is documentation only and never affects the build.

### How the stack is defined and consumed

Each `RENDER_STACK` group is an object with:

- `id` and `title` — the band's stable name and human label.
- `summary` / `satellite` — prose describing what the band owns and how it behaves under the raster.
- `palette` — the `COLOURS` sub-objects (or keys) the band reads.
- `layers` — the layer ids the band owns, both base-style and build-added.
- `steps` — an array of `{ when, run }` pairs: `when()` gates the step on a `FEATURES` toggle (or is always true), and `run(style, ctx)` applies it.

[`applyModifications(style, spriteKeys)`](../scripts/build.mjs) builds a shared `ctx` (the basemap sprite keys, passed to every step; only the POI icon rewrite reads it), then:

1. walks `RENDER_STACK` bottom-to-top, running every step whose `when()` returns true; then
2. walks `FINISHING_PASSES`, running every pass whose predicate is true.

`FINISHING_PASSES` is deliberately a separate list because its overrides must beat every group above — the imagery legibility pass is the only entry and the last thing that runs, gated by `SATELLITE_GROUND`, so its `setPaint` overrides win over the contours, roads and paths. The stack is the single source of truth for render order; mutating a group's metadata cannot change the output.
