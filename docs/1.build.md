# Build Script

> The `style.json` is generated by `scripts/build.mjs`.

```bash
npm install
npm run build
```

## Basemap Base

The build starts from the [OpenGIS Basemap](https://www.ogis.org/basemap/) — the OpenMapTiles OSM style pointed at OpenFreeMap planet tiles (upstream repo: [opengis/basemap](https://github.com/opengis/basemap)). The style is fetched from `https://www.ogis.org/basemap/style.json` (tracking upstream `main`), cached at build time, deep-cloned and mutated in place.

The basemap's sources, glyphs and sprite otherwise pass through untouched — the published basemap is already fully rewritten (glyphs and sprite point at `www.ogis.org/basemap`, tiles at `tiles.openfreemap.org/planet`). The sprite is re-wrapped into a two-sheet array (see [Sprites & Icons](12.sprites.md)): the basemap sheet keeps its `default` id so its own layer references are untouched, and the outdoors-owned sheet is added alongside. Attribution is the exception: the build owns every attribution string in [`ATTRIBUTION`](#attribution) and writes it to the live `openmaptiles` source and the basemap's `attribution` pseudo-source (a licence requirement), so the two cannot drift.

### Fetch & Cache

[`fetchBasemap()`](../scripts/build.mjs) downloads the basemap style with an HTTP ETag conditional GET:

1. Send `If-None-Match` with the cached ETag (`.cache/basemap-etag.txt`).
2. **304** — the cache is fresh; use `.cache/basemap.json`.
3. **200** — the file changed; download, re-cache and use it.
4. **Network error** — fall back to the cache with a warning (fail only if no cache exists).

The cache therefore auto-updates when upstream changes and works offline once primed.

[`fetchSpriteKeys()`](../scripts/build.mjs) fetches the basemap's `sprite.json` with the same conditional-GET pattern, caching to `.cache/basemap-sprite.json` with the ETag in `.cache/basemap-sprite-etag.txt`. Its keys seed the identity pairs of the basemap-POI icon matches (see [Sprites & Icons](12.sprites.md)).

Unlike the style, this fetch is non-fatal: a network error or non-OK response falls back to the cache, and with no cache the build proceeds without identity pairs — the curated pairs and fallback are zero-warning on their own.

## Structure

Each feature is one `apply…()` modification function that mutates the in-progress style, with two modes:

- **Restyle** — overrides the paint/layout of an existing basemap layer, matched by exact id ([`setPaint()`](../scripts/build.mjs)). Layers missing from the basemap are skipped silently, so the build stays robust against upstream renames.
- **Add** — inserts new sources/layers (DEM, contours, overlays), usually via [`insertAfter()`](../scripts/build.mjs)/[`insertBefore()`](../scripts/build.mjs) at a basemap anchor layer; some additions splice directly at a computed index or push to the end when the anchor is missing.

Every inserted layer's vertical position comes from its layer anchor, with direct splice/push as the best-effort fallback when the anchor is absent. The functions themselves are ordered by [`RENDER_STACK`](../scripts/build.mjs) — a single bottom-to-top array of render bands. Each band carries documentation metadata (`id`/`title`/`summary`/`palette`/`satellite`/`layers`) and a list of gated `steps`; a group with no steps has no band-level changes — `borders` is left to the upstream basemap, while `buildings` is still modified by `FINISHING_PASSES`. [`applyModifications()`](../scripts/build.mjs) walks the bands in order and runs each step whose predicate is true, then runs [`FINISHING_PASSES`](../scripts/build.mjs) — the cross-group overrides, with the imagery legibility pass last — so they beat every band above. The stack is the single source of truth for render order. See [Render Stack](10.render-stack.md) for the group-by-group table.

### Attribution

Every attribution string in the style is owned by one top-level [`ATTRIBUTION`](../scripts/build.mjs) config block beside `STYLE_NAME` — the build is the single source of truth, and the entries are defined in rendered order (basemap group → Mapterhorn → MapLibre → Esri):

- **`ATTRIBUTION.BASEMAP`** — the basemap credit (OpenFreeMap / OpenMapTiles / OpenStreetMap), set from one string on both the live `openmaptiles` source (the field MapLibre renders — a style-level attribution overrides the source's TileJSON) and the basemap's `attribution` pseudo-source (referenced by no layer, kept for licence compliance), so the two cannot drift.
- **`ATTRIBUTION.MAPTERHORN`** — the `©️ Mapterhorn` credit on the `demSource` raster-dem source ([`applyDemSource()`](../scripts/build.mjs)).
- **`ATTRIBUTION.MAPLIBRE`** — the ❤️ MapLibre link. Not attached to any source; the maps add it through the control's `customAttribution`.
- **`ATTRIBUTION.ESRI`** — the compact `©️ Esri` credit, attached to the `esri-satellite` raster source while the satellite ground feature is enabled ([`applySatelliteGround()`](../scripts/build.mjs)); the source — and so the credit — exists only then.

The build composes `ATTRIBUTION.LINE` — the applicable fragments joined by one space — and writes it into the generated `style.json` as `metadata.attributionLine`, merged into any upstream metadata rather than clobbering it. Composition sits **after** the `FEATURES` block so the satellite-ground toggle is in scope: the basemap, Mapterhorn and MapLibre fragments always join the line, and the `ATTRIBUTION.ESRI` fragment is appended **only when the satellite ground feature is enabled** (the Esri layer is what requires that credit). Apps and the screenshot harness pass that line as the map control's `customAttribution` (see [Compare App](13.compare-app.md#attribution)).

Because the line contains every source attribution verbatim, MapLibre's substring dedupe collapses each per-source entry into it, so the control renders one seamless line with no `|` separators.

With the satellite ground feature enabled the line is:

`❤️ OpenFreeMap ©️ OpenMapTiles ❤️©️ OpenStreetMap ©️ Mapterhorn ❤️ MapLibre ©️ Esri`

With it disabled the Esri fragment is absent and the line ends at `❤️ MapLibre`. Fragments are joined by a single space, and every copyright mark — including the conditional Esri one — uses the emoji presentation `©️` (U+00A9 + U+FE0F) rather than plain `©`.

Source-level attribution strings stay on their sources for licence compliance, and third-party consumers that load the style without reading the metadata still get maplibre's stock rendering — the used sources' attributions, length-sorted and `|`-joined. The only attribution literal outside the build block is the bare MapLibre fallback in the compare app and screenshot harness, used when `metadata.attributionLine` is unavailable.

### Constants & Config

The map and icon palettes live in [`palette.json`](../palette.json) at the repository root — the single source of truth for palette data. The build parses the file once and exposes its `map` block as `COLOURS` (`COLOURS = palette.map`), so layer code keeps reading tokens by feature (`COLOURS.<FEATURE>.<KEY>`) rather than hard-coding the palette colours. The `iconRoles`, `icons` and `iconOutline` blocks drive icon rendering (see [Sprite Sheet](#sprite-sheet)).

Each feature's non-colour configuration sits beside the `apply…()` function that consumes it — zoom ranges, opacities, widths, dash arrays and the like. The table below groups the main config families.

| Config group            | What it contains                                                                                                                                                                                                                                                           |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `palette.json`          | `map` tokens exposed as `COLOURS`; `iconRoles`, `icons` and `iconOutline` for the sprite workflow (see [Palette workflow](#palette-workflow)).                                                                                                                             |
| Ground raster & imagery | `SATELLITE_*`, `GROUND_RASTER_*` including the low/high ramp stops, `SAT_STRIP_LAYERS`, `WATER_TINT_OPACITY`, `IMAGERY_*` and `BUILDING_*`, beside the `applySatelliteGround()`/`applyGroundRetention()`/`applyWaterTint()`/`applyImageryLegibility()` group.              |
| POI expressions         | `POI_FILTER`, `POI_ICON_MATCH`, `POI_TEXT_EXPR`, `POI_SORT_KEY_MATCH` and the `PLANET_POI_*` equivalents, derived from the `OUTDOOR_POI` and `PLANET_POI` definitions in [`scripts/poi-config.mjs`](../scripts/poi-config.mjs) so the layers cannot drift from the config. |
| Waymarked routes        | `ROUTE_OVERLAY`, `ROUTE_WIDTHS`, `ROUTE_FILL_OPACITY`, `ROUTE_CASING_OPACITY`, `ROUTE_BADGE_GROUPS`, `ROUTE_ACTIVITIES`, `HIKING_ROUTE_TIERS` and `CYCLING_ROUTE_TIERS`, beside `applyRouteOverlay()`.                                                                     |

A few colour literals remain beside their config rather than in `palette.json`: `STYLE_LIGHT.color`, `BUILDING_OUTLINE_COLOUR`, `BUILDING_3D_COLOUR_RAMP`, `IMAGERY_*`, `ROUTE_BADGE_TEXT_COLOUR` and some POI paint colours.

## Satellite Ground

The `SATELLITE_GROUND` toggle places the style on the **Esri World Imagery** satellite raster: [`applySatelliteGround()`](../scripts/build.mjs) adds the `esri-satellite` source and `satellite` layer at the first water layer ([`waterStackIndex()`](../scripts/build.mjs)), falling back to directly above the `Background` floor, and [`applyWaterTint()`](../scripts/build.mjs) makes the water fills translucent. See [Ground Raster](11.ground-raster.md) for the Esri source details, blend rationale, opacity ramp and calibration.

> [!WARNING]
> **Esri attribution is a licence requirement.** While the satellite ground feature is enabled the build supplies the compact `©️ Esri` credit via `ATTRIBUTION.ESRI`, on the `esri-satellite` source's `attribution` field — never strip it.

### Retention & Legibility

[`applyGroundRetention()`](../scripts/build.mjs) runs [`removeLayers()`](../scripts/build.mjs) over the `SAT_STRIP_LAYERS` carry-over list, stripping any listed layer by exact id (missing ids are skipped silently, so upstream renames stay safe). While the raster is enabled, [`applyImageryLegibility()`](../scripts/build.mjs) runs as a [`FINISHING_PASSES`](../scripts/build.mjs) entry after every `RENDER_STACK` band, so its overrides beat the contours and the road/path styling. See [Ground Raster](11.ground-raster.md#ground-retention) for the retention rationale and [Imagery legibility](11.ground-raster.md#imagery-legibility) for the full pass.

> [!NOTE]
> The blend — raster above the vectors, water tint over the raster — is the project's flagship data-fusion example. See [Ground Raster](11.ground-raster.md).

## Roads

The `ROAD_SURFACE_AWARE` toggle restyles the basemap's road layers ([`applyRoadSurfaceAware()`](../scripts/build.mjs)) into a surface-aware hierarchy:

- **Tiered asphalt greys.** `ROAD_TIERS` groups the basemap's road fill layers into major (motorway/trunk/primary and their links), medium (secondary/tertiary and their links) and local (minor/service/track/raceway), each carrying a paved asphalt colour plus a light neutral-grey unpaved variant in `COLOURS.ROADS`. The paved fills lighten down the hierarchy — major is the darkest (`rgb(26, 26, 26)`), medium `rgb(36, 36, 36)`, local `rgb(48, 48, 48)` — so the most important roads read most strongly; the unpaved variants are light neutral greys (`rgb(150–156)`).
- **Lighter casings.** `ROAD_CASING_LAYERS` recolours the basemap's `* outline` layers — road, link, tunnel and bridge variants — from their vivid class hues (red motorways, green secondaries…) to neutral lighter greys (`CASING_MAJOR` `rgb(94, 94, 94)`, `CASING_MEDIUM` `rgb(106, 106, 106)`, `CASING_LOCAL` `rgb(120, 120, 120)`), so only the asphalt fills colour the network. Each casing takes its fill's engine width plus a screen-constant shoulder sliver on each side (`roadCasingWidthExpr()`), so narrow roads read stroke-dominant and wide roads show only a thin light edge.
- **True-scale width engine.** Each fill's `line-width` comes from the shared width engine (`roadWidthExpr()`), which renders real-world metres at true Web Mercator scale (reference latitude `ROAD_WIDTH_REFERENCE_LATITUDE`, so `px = metres × 2^z ÷ ROAD_METRES_TO_PX_Z0`). Widths resolve from a layer-id → metres lookup: `ROAD_WIDTH_KEYWORDS` (first match wins, casing ids resolving via their base layer) with `ROAD_WIDTH_OVERRIDES` pinning the ambiguous Link/Street bridge & tunnel ids to one width. A per-tier low-zoom floor (`ROAD_FLOOR_STOPS`), a mid-zoom boost and a high-zoom taper (`ROAD_WIDTH_FACTOR`) keep the network legible at the ends of the range; unpaved ways take `ROAD_UNPAVED_WIDTH_SCALE` of the metric branch via a paved/unpaved `case`. Pedestrian outlines are exempt and keep their basemap width. The style spec allows only one zoom-based subexpression per width, so the floor/true-scale max envelope is resolved numerically at each stop rather than nested as a `max` of two zoom interpolates. A butt line-cap keeps the rendering flush (round caps suppress interpolated dashes — the same quirk as the path family), and a solid dasharray is pinned so no basemap dash value leaks through.
- **Bridges & tunnels.** Bridge fills (`ROAD_BRIDGE_LAYERS`) mirror their tier's asphalt colour and the unpaved `case`, at the same engine width as their road class. Tunnel fills (`ROAD_TUNNEL_LAYERS`) take the tier's paved colour at a reduced `line-opacity` (`ROAD_TUNNEL_OPACITY`) so their dashes read, also at the engine width.

The under-construction fills and outlines are recoloured into the same greyscale family via `ROAD_CONSTRUCTION_FILLS` and `ROAD_CONSTRUCTION_OUTLINES`; only rail rendering is left to the basemap.

## Waymarked Routes

The `WAYMARKED_HIKING_ROUTES` and `WAYMARKED_CYCLING_ROUTES` toggles add the waymarked-route overlay in the `routes` band ([`applyRouteOverlay()`](../scripts/build.mjs)). Hiking and cycling are peer activities on one `outdoor-routes` vector source — `https://tile.ogis.app/routes/{z}/{x}/{y}.pbf`, source-layer `outdoor_routes`, z8–14. The style consumes `activity` (the feature's own activity), `activities` (the relation's full set in priority order) and `network` in the activity's own vocabulary; `ref`, falling back to `name`, labels the badges.

`applyRouteOverlay()` filters `ROUTE_ACTIVITIES` by the enabled toggles, registers the shared source once, and builds each activity's casing/fill pair per tier plus its badge symbol layers. Each descriptor supplies the toggle, colour, badge icon and tier table; `ROUTE_OVERLAY` supplies the source id, source-layer, tile URL, zooms, casing scale, line join/cap and insertion anchors. Layer ids derive from the source id and activity id: `outdoor-routes-<activity>-<tier>[-casing]` for lines and `outdoor-routes-<activity>-badges-<major|local>` for badges; there is no separate cycling namespace.

The whole block is inserted after the `Disputed border` linework; when that layer is absent it is inserted before the first label layer (`River labels`), and with neither anchor it is appended to the end of the stack.

> [!NOTE]
> **Legacy compatibility.** When `activity` is absent, the style infers it from `network` (cycling vocabulary → cycling, hiking vocabulary → hiking), then from a legacy `route_type=bicycle`, and finally defaults to hiking. Current tiles carry `activity`/`activities`; `route_type` is not part of the current contract.

See [Activities](7.activities.md) for the activity model, tier order, widths, opacities, colours and badge rules.

## Sprite Sheet

The style's `sprite` property is a two-sheet `{id, url}` array — the basemap's `default` sheet plus the outdoors-owned `outdoors` sheet — written unconditionally by [`build()`](../scripts/build.mjs) with absolute URLs. The build also rewrites the basemap's dynamic POI icon templates into a single `match` built from the real sheet keys. See [Sprites & Icons](12.sprites.md) for the sheet layout, the icon workflow, the route badge shields and the checker rules.

### Palette workflow

`palette.json` has four data blocks (plus a `version` field):

- **`map`** — the map paint tokens the build exposes as `COLOURS` (`TERRAIN`, `LANDCOVER`, `LANDUSE`, `WATER`, `PARK`, `ROADS`, `PATHS`, `ROUTES`, `CONTOURS`).
- **`iconRoles`** — named icon colours. A role is a hex value or an `@map.<TOKEN>` reference into the `map` block; the route roles reference `@map.ROUTES.HIKING`, `@map.ROUTES.CYCLING` and `@map.ROUTES.MIXED` so shields and linework stay in step.
- **`icons`** — the icon registry. Each entry names its `primary` role, an optional `detail` role and, for pale glyphs, `outline: true`. The presence of a key registers the icon.
- **`iconOutline`** — the shared keyline `role` and `width` used by icons with `outline: true` (see [Adding an icon](12.sprites.md#adding-an-icon)).

The authored sources are the SVGs in `icons/`, with `__primary__` and `__detail__` fill slots rather than literal colours. [`scripts/palette.mjs`](../scripts/palette.mjs) resolves the roles and writes rendered SVGs into gitignored `build/icons/`; `npm run palette:build` regenerates them, and `npm run palette:check` validates the sources and the palette — including role references, map references, unused roles, slot fills and the outline configuration — without requiring a rendered directory or `spreet`; it then verifies the committed `sprite.lock.json` (see [Building the sheet](#building-the-sheet--npm-run-spritebuild)).

The palette workflow is edit `palette.json` and/or `icons/` → `npm run palette:build` (optional; `npm run sprite:build` renders first) → `npm run sprite:build` (which also rewrites `sprite.lock.json`) → `npm run build` → `npm run demo:build`. `style.json`, the sprite sheets in `dev/public/` and `sprite.lock.json` are committed; the rendered icons in `build/icons/` and the app bundle in `dist/` are generated. See [Adding an icon](12.sprites.md#adding-an-icon) for authoring an icon and [Outdoor POIs](4.pois.md) for the checker.

### Building the sheet — `npm run sprite:build`

[`scripts/build-sprite.mjs`](../scripts/build-sprite.mjs) first renders the palette icons through `writeIcons()` in [`scripts/palette.mjs`](../scripts/palette.mjs) into `build/icons/`, then runs the native `spreet` binary (brew `flother/taps/spreet` — the same sprite tool the basemap repo uses via openmaptiles-tools, installed locally, no docker) over the SVGs in `build/icons/`, writing the 1x sheet plus the `@2x` retina sheet into `dev/public/` (`sprite.{json,png}` and `sprite@2x.{json,png}`). It then verifies the sprite keys exactly match the registry in `palette.json` (`paletteIconNames()`), failing the build on a mismatch — there is no separate hard-coded icon list. The SVGs' fills are rasterised into the PNG sheets, so glyph colours are baked in: the sheet is not an SDF atlas, and style `icon-color`/`icon-halo-*` paint cannot recolour it. Pale glyphs carry their contrast as a baked keyline (see [Adding an icon](12.sprites.md#adding-an-icon)). The sprite files and `sprite.lock.json` are committed; Vite copies `dev/public` → `dist/` on `demo:build`, so the sheet deploys to `https://www.ogis.org/outdoors/sprite`. Because that URL is absolute and only exists after the app deploys, the icons render once the site is deployed (push to master → GitHub Pages). The screenshot harness serves the same files from `dev/public/` (see [`scripts/screenshots/generate.mjs`](../scripts/screenshots/generate.mjs)).

After the key check succeeds, [`writeSpriteLock()`](../scripts/sprite-lock.mjs) rewrites `sprite.lock.json` with sha256 digests of the sprite sources (`palette.json` and the sorted `icons/*.svg`) and of the four committed sheets in `dev/public/`. CI cannot run `spreet`, so it cannot rasterise the sheet; `npm run palette:check` instead re-hashes those inputs and outputs, failing when the lock is missing or any digest differs and naming the missing lock or stale entry. The lock is generated output — never hand-edit it; regenerate it with the sprite build.

## The Output

[`build()`](../scripts/build.mjs) fetches the basemap and the default sprite keys, sets the root `name` to `"Outdoors"` (`STYLE_NAME`), applies attribution and metadata, writes the sprite array, applies the modifications, writes `style.json` and validates it:

1. **Fetch** — [`fetchBasemap()`](../scripts/build.mjs) and [`fetchSpriteKeys()`](../scripts/build.mjs) (both ETag-cached, see above; the sprite fetch is non-fatal).
2. **Identity** — the basemap is deep-cloned and the root `name` property is set to `"Outdoors"`, overriding the basemap's own name.
3. **Attribution** — `ATTRIBUTION.BASEMAP` is synchronised onto the live `openmaptiles` source and the basemap's `attribution` pseudo-source.
4. **Metadata** — `metadata.attributionLine` is merged into the style metadata.
5. **Sprite** — the root `sprite` property is replaced with the two-sheet array (see [Sprites & Icons](12.sprites.md)); this always applies.
6. **Modifications** — [`applyModifications()`](../scripts/build.mjs) walks the [`RENDER_STACK`](../scripts/build.mjs) bands in order, then runs the [`FINISHING_PASSES`](../scripts/build.mjs) overrides.
7. **Write** — `style.json` at the project root.
8. **Validate** — the written file is checked against the MapLibre Style Specification ([`validateStyle`](../scripts/validate-style.mjs)); a failed validation exits 1, but the file has already been written, so the invalid `style.json` remains on disk.

The result is a single `style.json` at the project root — the only file the style needs to ship. It is not self-contained: it references remote vector and raster tiles, glyphs and two remote sprite sheets.

> [!NOTE]
> **Why paint expressions instead of filters?** The `contour-lines` layer draws both index and minor contours, using `case` paint expressions to style each tier and hide lines off the 20 m minor cadence at opacity/width 0 rather than splitting the tiers into filtered layers. See [Elevation & Terrain](5.dem.md).

## Screenshots

The named JPEGs in `screenshots/` (embedded across these docs and the README) are generated by [`scripts/screenshots/generate.mjs`](../scripts/screenshots/generate.mjs), which serves a small MapLibre harness plus the built style and the committed outdoors sheet over a free local port, then drives headless Chromium via Playwright. Shot definitions — centre, zoom, bearing, pitch, size, scale and any canvas cap — live in [`shots.json`](../scripts/screenshots/shots.json); `npm run screenshots` renders them all, `--name <id>` renders one; a run exits non-zero on a capture failure, including a filtered `--name` run.

The harness rewrites the `outdoors` sprite URL in the served style to the locally built `/sprite`, so a run verifies the icons committed with the code rather than the deployed sheet; the basemap `default` sheet stays remote.

The shots cover the road palette, urban fade, 3D building massing, marked route linework and badges, and the unmarked tier; definitions live in [`shots.json`](../scripts/screenshots/shots.json).

[`check.mjs`](../scripts/screenshots/check.mjs) verifies the committed set without rendering: it validates `shots.json`, checks each JPEG's magic bytes and dimensions, confirms README and docs image references resolve, and warns about orphaned or unreferenced images.

Pass `--stale` to also fail when an image is older than `style.json` or the screenshot/build inputs — run `npm run build` first.
