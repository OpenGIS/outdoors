# Performance

> A Playwright-driven benchmark for the compare app — camera-driven draw performance and cold-to-warm load timing — and the DEM source and terrain-LOD optimisations it validated.

## Overview

[`scripts/bench/bench.mjs`](../scripts/bench/bench.mjs) measures MapLibre performance of the compare app on the real GPU: a **headed** Chrome launched through Playwright at a forced device scale factor, against its own ephemeral Vite server. It exists to make style and terrain changes measurable — record a baseline, apply a component-ablation variant, compare medians.

The harness has two modes sharing the same launch, viewport and JSON report. **Move** (the default) measures sustained draw performance: it boots the app on a free port in the 11001–11999 range (11000 is reserved for a session dev server), waits until both maps are loaded with no tiles in flight, then drives the camera and samples `requestAnimationFrame` deltas plus each map's `render` count. **Load** measures navigation to fully rendered: each round runs a cold load in a fresh browser context (empty HTTP cache) followed by warm reloads in the same context, with no camera movement. Load mode can benchmark the production `demo/` bundle through `vite preview` as well as the dev app.

The harness reads the maps from inside the page — the compare app's `window.__outdoorsMaps` hook, or Vue's dev-only `__vueParentComponent` setup state in `dev/` — and all timing happens inside the page, so CDP round-trips don't distort it.

## Running the benchmark

```bash
npm run bench
npm run bench -- --shot bolzano-3d --variants full,no-right-terrain --rounds 1 --duration 3000
npm run bench -- --mode load --shot bolzano-3d --rounds 1
npm run bench -- --mode load --serve demo
```

Bare `npm run bench` runs every shot × every variant over 3 interleaved rounds in move mode.

| Flag                   | Default | Meaning                                                                                                       |
| ---------------------- | ------- | ------------------------------------------------------------------------------------------------------------- |
| `--mode`               | `move`  | `move` = camera-driven draw benchmark; `load` = navigation-to-settled load timing                             |
| `--serve`              | `dev`   | Load mode only: `dev` serves `dev/` via Vite; `demo` serves the production `demo/` bundle via `vite preview`  |
| `--shot`               | `all`   | Shot / scenario to run; `all` means every shot in move mode, or the default load set in load mode (see Shots) |
| `--variants`           | `all`   | Move mode: comma-separated variant names (see below)                                                          |
| `--rounds`             | `3`     | Interleaved rounds per shot — drift is spread across variants rather than clustered on one                    |
| `--duration`           | `6000`  | Move mode: measured camera-motion window per run (ms)                                                         |
| `--cap`                | `60000` | Load mode: hard cap per load (ms)                                                                             |
| `--warm`               | `1`     | Load mode: warm reloads after each cold load                                                                  |
| `--dpr`                | `2`     | Device pixel ratio; each DPR is a separate Chrome launch                                                      |
| `--screenshot <label>` | —       | Capture-only mode: load each shot, settle, write `quality-<shot>-<label>.jpg`, no measurement                 |

The default viewport is 1640×777 CSS at DPR 2 — the recorded baseline size. The window is calibrated against the measured OS chrome so the page lands on that target rather than an approximate one.

In move mode each shot runs `rotate` for every variant, then `pan` and `idle` for `full` only. `idle` is a fixed 3 s sanity run: it expects no camera motion and asserts the on-demand renderer stays quiet.

In load mode each round opens a fresh browser context and runs one cold load plus `--warm` warm reloads; a throwaway warm-up load precedes the measured runs so the Vite module-transform cache is warm. A load ends when it is **quiet** — both maps report `loaded()`, neither is moving, and no request has been in flight for 1000 ms — or when `--cap` is hit.

### Shots

- `bolzano-3d` — pitched high-zoom 3D city (z16, pitch 60).
- `dolomites` — top-down provincial view (z13).
- `dolomites-3d` — pitched relief (z13, pitch 60).
- `motorway` — mid-zoom pitched motorway (z13.5).

Move mode's `--shot all` runs every shot; load mode defaults to the three that carry the most tile work on a fresh visit — `motorway`, `bolzano-3d` and `dolomites-3d`. Every run seeds the compare app before mount with the Esri provider, the side-by-side view and both DEM toggles on.

### Variants

Each move-mode variant is a component ablation applied page-side, so it runs against the same loaded style:

- **Whole scene** — `full`; `left-only` / `right-only` detach the compare sync to isolate one pane.
- **DEM** — `no-left-dem` (untick both left DEM overlays), `no-right-terrain` (`setTerrain(null)` on the right map), `no-right-hillshade` (remove `hillshade-layer`), `no-raster-ground` (remove the `satellite` layer, revealing the natural-earth vectors beneath; the layer exists only when the satellite ground feature is enabled).
- **Layers** — `no-buildings` (remove `building-3d`), `no-contours` (remove `contour-lines` and `contour-labels`), `no-overlays` (remove the `outdoor-poi` / `outdoor-paths` layers).
- **Symbol families** — `no-symbols` (hide every symbol layer) plus one variant per family (`no-place-labels`, `no-road-labels`, `no-poi-labels`, `no-path-labels`, `no-contour-labels`, `no-park-labels`, `no-misc-labels`). Families hide layers rather than removing them so collision and placement stay on the same code path as the full run. `no-path-labels` is intentionally empty: the built style defines no symbol layers on the `outdoor-paths` source, and the harness reports the zero count rather than inventing one.
- **Terrain LOD** — `lod-tight-a` (6, 2) and `lod-tight-b` (2, 1), applied to both maps' DEM sources via `setSourceTileLodParams()`.

### What it measures

**Move mode** — per run: mean FPS (from the rAF deltas), frame-time p50 / p95 / p99, the percentage of frames over 25 / 33 / 50 ms, and the `render` event count for each map. Results are aggregated as medians across rounds and printed as a summary table.

**Load mode** — per load: the marker timeline (DOMContentLoaded, `load`, first `.maplibregl-canvas` in the DOM, maps reachable, `loaded()`, `areTilesLoaded()` and quiet), frame-gap stats over the load, render counts, and per-host request/byte accounting from Playwright's network events. Those events are authoritative for request counts and bytes — MapLibre fetches tiles in workers, so Resource Timing is only a cross-check. Results print as medians per shot and load kind (cold/warm), with a per-host breakdown.

A JSON report is written to `.opencode/tmp/bench/<ISO>.json`, carrying the mode-specific summary (`summary` for move; `load.summary` and raw `load.runs` for load), the raw per-frame samples, the environment probe (viewport, DPR, user agent, WebGL renderer and vendor, hardware concurrency), console errors, HTTP 4xx/5xx responses and any failures. A move run fails if a variant does not apply cleanly or the idle sanity check sees unexpected renders; failed loads are recorded in `failures` and exit non-zero.

> [!NOTE]
> The move-mode method — warm-up, sampling and camera drives — deliberately mirrors a prior manual profiling pass, so numbers stay comparable with the recorded 1640×777 baseline.

## Recorded baseline

> [!NOTE]
> **Environment.** All figures below were measured on an Intel UHD 630-class integrated GPU running the dual-map compare app — a deliberately low-end target. Absolute values will vary on other hardware; for move mode the variant ratios are the portable result.

### Move mode — draw performance

Medians of 3 rounds at DPR 2 in rotate mode, against the compare app with both left DEM toggles on. "Before" is the pre-optimisation figure.

| Shot           | FPS  | p50 ms | Before   |
| -------------- | ---- | ------ | -------- |
| `bolzano-3d`   | 7.6  | 116    | 6.3–6.6  |
| `dolomites`    | 15.0 | —      | 12.7     |
| `motorway`     | 16.0 | —      | 14.6     |
| `dolomites-3d` | 10.5 | —      | new shot |

`idle` sat at ~60 fps with **0 map renders on every shot**, confirming on-demand rendering stays intact.

### Load mode — cold and warm loads

Medians of 3 rounds at DPR 2 with one warm reload per round, recorded against the built `demo/` bundle served through `vite preview` (`--mode load --serve demo`). `loaded` is MapLibre's `loaded()` mark; quiet marks the point both maps are loaded, stationary and free of in-flight requests for 1000 ms. The run predates the DEM source `maxzoom` change, so `bolzano-3d` carried seven Mapterhorn 404s per load; the other shots had none.

| Shot           | Cold `loaded` | Cold quiet | Warm `loaded` | Warm quiet |
| -------------- | ------------- | ---------- | ------------- | ---------- |
| `bolzano-3d`   | 4.8 s         | 5.9 s      | 4.9 s         | 6.1 s      |
| `dolomites-3d` | 5.5 s         | 6.5 s      | 5.5 s         | 6.7 s      |
| `motorway`     | 3.0 s         | 4.2 s      | 2.3 s         | 3.4 s      |

Dev-serve numbers are not comparable: Vite serves unbundled modules, which roughly doubles the bytes transferred per load. The full per-host request, byte and last-response-end breakdown for each run lives in the JSON report.

## Findings

- **The right pane's 3D terrain drape dominates.** Removing it was ≈2.1–2.5× faster at pitched `bolzano-3d` and 1.3–1.6× at `motorway` — the single largest cost in the scene.
- **The global symbol / label placement pass is next.** Hiding every symbol layer was ≈1.3× at `bolzano-3d` and ~2× at `motorway` / `dolomites`. No single label family mattered — the cost is the pass itself, not any one family.
- **Minor levers.** 3D buildings ≤1.09×, contours ~1.1×, hillshade ~1.1×, raster ground ~1.05–1.17× (the satellite ground layer blended over the natural-earth vectors).
- **Not fill-rate bound.** Dropping DPR 2→1 gained only 1.17×, so the bottleneck is per-frame CPU / tile work rather than fragment throughput.
- **Idle is free.** Zero renders at rest on every shot.
- **Tile-service protocol check (September 2026).** A verification of the `tile.ogis.app` service enabled HTTP/2 behind a cache lock and measured single-user warm loads at protocol parity — uncapped HTTP/2 matched an HTTP/1.1 configuration capped at six sockets. The contour load tail is response-duration-bound: cold requests were issued in a ~16 ms wave and their responses completed in a tight band regardless of tile size, so connection and protocol limits are not the binding constraint.

## Adopted optimisations

Three levers came out of this programme and are now in place.

### DEM `tileSize` declared at 256

Mapterhorn serves 512 px Terrarium-encoded WebP tiles, but the style declares the `demSource` raster-dem at 256 (`DEM_SOURCE_TILESIZE` in [`scripts/build.mjs`](../scripts/build.mjs)). Halving the declared tile size cuts the terrain mesh and hillshade texture work to build — measured at ~+23% fps at pitched high-zoom views with no perceptible quality change. See [Elevation & Terrain](5.dem.md).

### DEM `maxzoom` declared at 15

Mapterhorn's z16 coverage has gaps, and the resulting 404s left the terrain mis-sampled at pitched high-zoom views — the build script gives the example of Bolzano. The style therefore declares `DEM_SOURCE_MAXZOOM = 15` in [`scripts/build.mjs`](../scripts/build.mjs), so MapLibre overzooms complete z15 tiles rather than requesting the gap-ridden z16 — no 404s, consistent terrain, and visually indistinguishable in stills. The compare app's `compare-dem` source matches the declared maxzoom so both panes overzoom the same tiles. See [Elevation & Terrain](5.dem.md).

### Terrain level-of-detail

[`dev/src/terrainLod.js`](../dev/src/terrainLod.js) exports `TERRAIN_LOD = { maxZoomLevelsOnScreen: 6, tileCountMaxMinRatio: 2 }` and an `applyTerrainLod(map, sourceId)` helper. It lowers MapLibre's `setSourceTileLodParams()` defaults (9.314, 3.0), capping the DEM zoom-level spread and the number of tiles requested at high pitch — fewer, coarser tiles where the horizon is visible. Measured at **+11%** on pitched views and inert at pitch 0, so it costs nothing where it does not apply. The helper is feature-guarded (older MapLibre without the API degrades gracefully), checks the source exists, and is idempotent.

> [!IMPORTANT]
> **Consumer tip.** `setSourceTileLodParams()` is a **map-level** option, not a style property — it cannot ride in `style.json`. Consumers of the style must apply it to their own DEM source after the map loads. The compare app does this in [`dev/src/App.vue`](../dev/src/App.vue) (right map, derived from the parsed style's `raster-dem` sources) and [`dev/src/composables/useDemOverlay.js`](../dev/src/composables/useDemOverlay.js) (left map's `compare-dem`). See [Client-side rendering](6.client.md#dem-overlays).
